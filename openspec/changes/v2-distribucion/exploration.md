## Approaches

### 1) Go-standard distribution: `go install` + binary release via CI + E2E install + `init` offline test (recommended)

- **Description:** Reinterpret F-01 as Go equivalent: `go install github.com/HectorCortes/haro@latest` is the "global install" (Go's `GOBIN` analogue of `pnpm add -g`), and a CI `release` workflow publishes a statically linked `haro` asset (`go build -o haro`, already produced as `./haro`) on tags via a minimal `release.yml` *or* via documented manual `go install` only (no `goreleaser` initially). Criterion's verifiable intent is preserved: "installation works in a clean environment without additional manual steps" -> verify by scripting a clean `t.TempDir()` (or Docker) with `GOBIN=$(mktemp -d) go install …@latest` (or `go build -o $TMP/haro .`) and assert `haro` resolvable and `haro init` + `haro --help` succeed; also verify `go build ./...` produces a complete binary. F-02 verified by a gate script proving repo contains no `package.json`/`postinstall`/`prepare`/`prepublishOnly`/`install` hook (and that `go install` has no such hook). F-03 verified by E2E `haro init` in an empty `t.TempDir()` with `GONOSUMDB=*`/`GOPROXY=off` / `unshare -n` (no network) asserting `.haro/config.yaml` + dirs exist and rerun is idempotent. Document in `README.md` the canonical install line (`go install github.com/HectorCortes/haro@latest`) and release assets.
- **Pros:** Directly satisfies III.1 (ecosystem change authorized) and AGENTS.md pure-Go/no-cgo + "dependency installation via standard package manager" (Go toolchain is itself the standard manager — `go install` is `go`'s `npm install -g` analogue). Zero new runtime dependencies; binary already statically linked. Uses existing `ci.yml` pattern; one small `release.yml` or even docs-only initially keeps risk minimal. Aligns with `v2-store`'s `single-pr`/`size:exception` precedent — coherent, reviewable, and personally owned repo allows direct push. F-02 trivially passes (no install script to disable). F-03 needs only a new E2E, no code.
- **Cons:** `go install @latest` requires network for `go install` verification at test time (ironically) unless the E2E builds from the local checkout (`go build -o`). Proposal must distinguish "haro init offline" (P1, no network) from "go install needs network" (expected, not tested offline). If a full release job is added, tag discipline and `GITHUB_TOKEN` perms (`contents: write`) are new. Without `goreleaser`, multi-arch assets (darwin/arm64) are not auto-built — acceptable for v2 scope.
- **Effort:** Low. Docs + one workflow file (or none) + 2 E2E tests + one gate script. ~150-300 lines.

### 2) Document-only reinterpretation: tests E2E for F-01/F-03 without touching infra

- **Description:** Keep CI exactly as today (no release job). Reinterpret F-01 in the change's spec prose as "`go build ./...` produces a resolvable `haro` binary" and prove it with `go test -run TestDistribution_InstallE2E` that runs `go build -o $TMP/haro .` + `haro init` in a clean `t.TempDir()` and asserts binary + init. No `release.yml`, no `goreleaser`, no published asset. Regard `go install github.com/HectorCortes/haro@latest` as documented but not CI-tested (or tested via `go list` only). F-02 gate and F-03 offline test as in Approach 1. Update `README.md` to say installation is `go build` / `go install`.
- **Pros:** Minimal diff, zero CI risk, satisfies F-01's *literal* verification alternative "`npm run build` produces a complete `dist/`" by translating to "`go build` produces a complete `haro`". Fastest to archive; respects `AGENTS.md:14` "no third-party installation scripts" by adding nothing.
- **Cons:** Leaves "distribution mechanism is the current one — global npm package" literally unaddressed as a published artifact; a strict auditor could argue distribution still unpublished. Does not give users a downloadable asset without Go toolchain. Smaller real value than Approach 1 if users expect a binary release.
- **Effort:** Very Low. Docs + 2 tests + gate script. ~80-150 lines.

### 3) Full-release tooling: `goreleaser` + multi-arch + Homebrew

- **Description:** Add `goreleaser` config (`.goreleaser.yaml`), a `release.yml` on `push: tags: ['v*']` that runs `goreleaser release --clean` producing tarballs + checksums + Homebrew formula update. Bin `haro` cross-compiled for `linux/amd64, linux/arm64, darwin/amd64, darwin/arm64`. Verification: install in clean Docker (`go install @latest` *and* curl release asset) + `haro init` without network.
- **Pros:** Polished distribution; multi-arch assets; Homebrew `brew install haro`. Aligns with pure-Go binary distribution best practices.
- **Cons:** Adds `goreleaser` as CI-only tool (not runtime dep, but a third-party action: `goreleaser/goreleaser-action` — permissible but widens CI attack surface; AGENTS.md policy is "no third-party installation scripts that execute external code *incorporated into the repo*" — a GitHub Action is borderline. Tag workflow + `contents: write` perms need review. Over-engineering for a personal repo with direct-push workflow and no users beyond the owner. Multi-arch cross-compile needs testing (QEMU). Size overhead: config + workflow + assets tests ~400-600 lines. Prior series (`v2-spike-go` … `v2-store`) always preferred stdlib/Minimal — this breaks that spirit.
- **Effort:** Medium-High. New config + workflow + multi-arch E2E + Homebrew. Larger review, more maintenance.

### 4) Literal npm retention (manufacture `package.json` wrapper around Go binary)

- **Description:** Keep the npm literal by creating `package.json` with `bin: "dist/index.js"` that wraps the Go binary (e.g., `postinstall` downloads or `dist/index.js` is a JS shim that `spawn`s the Go `haro` binary via `bin/haro`), preserving `files: ["dist"]`, `prepublishOnly: "npm run build"`. Publish to npm registry as `shardeo`/`haro`. F-01 then passes literally.
- **Pros:** Zero reinterpretation; Deltas text satisfied byte-for-byte.
- **Cons:** **Contradicts AGENTS.md pure-Go** and `modernc.org/sqlite` no-cgo premise; introduces Node/npm as required toolchain for a Go project; introduces exactly the `postinstall` attack vector F-02 forbids (downloading/executing Go binary from npm). Violates constitution III.1's spirit (which says distribution *may* change) by clinging to v1. Introduces `package.json` + `node_modules` + `dist/` overhead solely to satisfy outdated wording. No prior change in the series introduced npm/Node (all 7 archives are pure Go). Strong negative: would force `AGENTS.md` security posture violation.
- **Effort:** Medium (wrapper, build, publish) with High negative value. **Not recommended; documented only to make explicit why it is rejected.**

## Recommendation

**Adopt Approach 1 (Go-standard: `go install` + binary release via CI + E2E gates).**

**Justification:**

- **Constitutional grounding:** `haro-constitucion.md:III.1` explicitly authorizes changing the distribution ecosystem. `AGENTS.md:5` places constitution alongside contract as source of truth — preservation of the *intent* of F-01 (install in clean env without manual steps, binary resolvable) matters more than preservation of the *syntax* `pnpm add -g / dist/index.js`. The 92-criteria contract is binding, but III.1 tells us the contract anticipated this change.
- **AGENTS.md alignment:** Stack is `Pure Go, no cgo` with CLI binary + `modernc.org/sqlite`. Dependency installation goes through standard package manager — for Go that is `go install` / `go build`, not `pnpm`. Adding npm would contradict the stack definition and the explicit `AGENTS.md:15` security posture (`no third-party installation scripts … that execute external code`).
- **Verified current behavior closes 2/3 criteria already:** `project.Init` offline/local proof (`internal/project/init.go:15-39`, `strace` network-zero, `init_test.go` idempotence, `e2e_test.go:12-21` temp-dir proof) means F-02 + F-03 are *already* satisfied; the remaining work is gates/tests, not implementation. This keeps the change small.
- **Value vs size in a personal repo:** Approach 1 delivers real user value (one-line `go install github.com/HectorCortes/haro@latest` + optional release asset) with ~150-300 lines, within the `200000` review budget and the `single-pr` direct-push model. It avoids Approach 3's over-engineering (multi-arch/homebrew) and Approach 4's npm regression, while improving on Approach 2 by providing a *published* mechanism (CI release or at least documented install) so F-01's "distribution mechanism is the current one" claim is defensible to an auditor.
- **Precedent from the series:** `v2-store` delivered the last 2 DDL tables atomically because F-02 required literal schema inspection; `v2-path-claims` eagerly created `path_claims` DDL even though broker wait-queue is deferred. Analogously, eagerly documenting/testing `go install` + binary now (even if `goreleaser` multi-arch is deferred) follows the same "verify-not-redefine" / "DDl-pure now, runtime deferred" spirit.

**Scope for proposal:** The proposal must explicitly frame F-01 reinterpretation as *compliant evolution under III.1*, not a contract deviation. It should note the 4 interpretation options (a)-(c) + wrapper, select (b), and state that F-02/F-03 are behavioral passes requiring only gates/E2Es. It must enumerate out-of-scope (`shardeo doctor/setup/CLI registration in config.yaml`, `v2-broker`/`v2-ipc`, PTY, multi-user, Homebrew/goreleaser multi-arch deferred) and include a rollback plan (`git rm` the release workflow + revert `README.md` — no `go.mod` impact).

## Risks

- **Contract-literalist audit reading of F-01 (MEDIUM, mitigable):** An auditor reading Deltas byte-for-byte could insist "global npm package (`pnpm add -g shardeo`)" means npm registry, not `go install`. Mitigation: proposal explicitly cites `haro-constitucion.md:III.1` as constitutional override and frames Go reinterpretation as preserving verifiable intent (clean-env install without manual steps, binary resolvable). If strict literalism persists, propose a minimal `deltas-acceptance.md` amendment changing the F-01 example parenthesis to "e.g. `go install github.com/HectorCortes/haro@latest` or equivalent published binary" while preserving the criterion's intent.
- **CI/release permission escalation (LOW if docs-only, MEDIUM if release job):** Adding `release.yml` with `contents: write` widens CI perms vs current `contents: read`. Mitigation: Approach 1 can start as docs-only (no release job) and add the minimal `release.yml` later; if added, scope perm to `contents: write` only in `release` job and pin action SHAs.
- **Over-scoping `goreleaser`/Homebrew (LOW if deferred, MEDIUM if taken):** Approach 3 tempts polishing prematurely. Mitigation: proposal explicitly defers `goreleaser` + multi-arch + Homebrew as future additive change, documenting "binario autocontenido via `go build` suffices for v2" (constitution III.2 local tool). The gate script should not assert multi-arch.
- **`hare` vs `shardeo` naming drift (LOW):** Deltas says `shardeo` everywhere, Haro binary is `haro`, dirs `.haro`. Mitigation: proposal notes v1→v2 rename is global (constitution) and F-01/F-03 apply to `haro`; no alias `shardeo` needed.
- **Network assumptions in E2E tests (MEDIUM):** `go install @latest` needs network; F-03 explicitly requires `init` *without* network.
