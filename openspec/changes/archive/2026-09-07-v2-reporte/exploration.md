# Exploration: v2-reporte — Change reporting

## Current State

### Normative contract
- **Deltas `deltas-acceptance.md:392-409`** defines 4 criteria:
  - **F-01 [E2E] P0**: when top-level execution finishes, system computes/shows which files changed relative to starting point; `execution.report {execution_id}` → `{changed_files: string[]}`.
  - **F-02 [E2E] P1**: computed **once, only at top level** — never per nested workflow.
  - **F-03 [INT] P1**: accuracy against real `git status` / `git diff --name-status` for new/modified/deleted (and renamed if applicable).
  - **U-01 [UNIT] P1**: diff computation by table — `changed_files` compares starting point (base/commit) with final state covering new/modified/deleted/renamed, tested with real git in temp dirs.
- **Tracking row `deltas-acceptance.md:488-489`**: `v2-reporte | 4 | 1 | pending` — next after `v2-composicion` (archived 2026-09-06, `openspec/changes/archive/2026-09-06-v2-composicion/archive-report.md:88` recommends `v2-reporte` next, CLI-direct compatible).
- **`docs/v2/haro-constitucion.md:155-158` §IX.5**: IX.5.1 top-level execution (invoked by external orchestrator) reports files changed relative to starting point; IX.5.2 computed once at top level, never per nested workflow. **§I.6 (`:14-16`)**: Haro coordinates and reports; never integrates/publishes/discards — report is read-only. **§X (`:160-188`)**: composition is flattened (single `execution_id`, `X.1.2`, `X.2.1` namespacing) — report must compose with exactly one execution (F-02 trivially satisfied if no child executions exist, which `v2-composicion` guarantees).
- **`docs/v2/haro-especificacion-tecnica.md:517`** §6 table: `execution.report | CLI→Broker | {execution_id} | {changed_files: string[]}`. DDL §2 (`:129-258`) shows **no reporting column/table**; §7.3 (`:562-563`) documents `path_claims` ownership but mentions no `execution.report` persistence. §1/§2 confirm execution/step/attempt/generation model and `executions.workspace_root` as physical path.
- **`docs/reference/SPECS.md`** (v1 oracle): no `report`/`changed_files`/`artifact diff` behavior — greps for `report, changed, diff, artifact` return only `git diff` audit traces and bundle manifests. v1 Shardeo had `.shardeo/artifacts/` with `requires/produces` validation but no worktree diff reporting. This is **net-new** for v2; nothing to preserve.

## Gaps vs Criteria

| Criterion | Expected | Current | Gap |
|-----------|----------|---------|-----|
| **F-01** report at top-level completion, `execution.report → {changed_files}` | Computes changed files relative to starting point when execution finishes; shows them to user; `execution.report` RPC/CLI returns `string[]`. | No report computation, no RPC, no CLI, no `changed_files` persisted or computed. Execution only tracks `status` (`pending→running→completed|failed` via `resyncExecution`). | Entire feature missing. Need diff engine + CLI/Store surface. |
| **F-02** once, only top level | Single report per execution, not per internal `workflow` node. | No reports at all; with flatten no child executions exist so F-02 is vacuous today, but a naive per-step report loop would violate it. | Must ensure report is execution-scoped, invoked once (either persisted at terminal or computed idempotently on demand and counted as logical single). |
| **F-03** accuracy vs `git status`/`git diff --name-status` for new/modified/deleted/(renamed) | Report lists exactly the workspace changes vs starting point, verified by fixture running both. | No diff logic. Unclear handling of untracked files, deletes, renames, and `.haro/` internals. | Need git-diff strategy that matches real git, incl. untracked. |
| **U-01** diff by table (base vs final, 4 change types) | Table tests over temp git repos. | No diff function to test. | Need pure `changedFiles(repoRoot, workspaceRoot, baseCommit) ([]string, error)` unit. |

Cross-cutting gap: **starting point is undefined and uncaptured**. Deltas say "base/commit" and constitution "starting point" without specifying: is it `HEAD` SHA at `CreateExecution`, the worktree's `HEAD` (detached), `executions.workspace_root`'s committed tree, or a captured snapshot? `manager.go:46` does `git worktree add --detach <dest> HEAD` — the worktree's `HEAD` is a detached copy of the invoking repo's `HEAD` at that instant. If that SHA is not captured before steps mutate files, and the worktree is removed at `resyncExecution:1019-1023`, there is no anchor to diff against. `executions` row has no `base_commit/base_sha/created_commit` column to persist it.

## Approaches

### 1) On-demand `git`-binary diff at report time (recommended shape)
- **Description**: Persist `base_commit` (SHA of `HEAD` at `CreateExecution`) in `executions.base_commit` (nullable, backfilled). `Engine.Report` shells out with `exec.CommandContext` fixed argv (like `worktree.Manager`) to run in the execution's `workspace_root` if it still exists, otherwise in `cwd` with `--work-tree` fallback: `git diff --name-only --diff-filter=ADMR --find-renames --no-renames?` + untracked handling via `git ls-files --others --exclude-standard` or `git status --porcelain=v1`. Normalize paths to repo-relative, sort, de-dupe, exclude `.haro/` by default, return `changed_files: string[]`. CLI `haro report <id> --json` calls `Engine.Report`; `execution.report` JSON-RPC (when broker arrives) will delegate to same engine method. No persisted report column — idempotent on demand satisfies F-02 (logical once, computed when requested after terminal).
- **Pros**: Simple, truthful to git; no background job; untracked files handled explicitly; works for `isolated` (worktree) and `shared` (repo root) uniformly; pure Go unchanged except `exec`; table-testable with real repos.
- **Cons**: Requires `base_commit` migration; if worktree was already removed by `resyncExecution:1019-1023`, diff must use `git diff <base> HEAD` from repo root or handle missing worktree — extra branch. Relies on git binary availability (acceptable: `manager_test.go:47` already gates on `git`).
- **Effort**: Medium. One nullable column, one diff helper, one CLI handler, table tests.

### 2) Persist-at-terminal (compute once, store `changed_files`)
- **Description**: Hook `resyncExecution` after setting `status=completed|failed` but **before** `worktreeMgr.Remove`: run same `git diff` logic, marshal `changed_files` JSON into new `executions.changed_files TEXT` (or separate `execution_reports(execution_id PK, changed_files TEXT, computed_at TEXT)`). `execution.report` then is a pure DB read, guaranteeing F-02 "computed once" literally (write-once, subsequent reads return stored value; concurrent callers get same snapshot). Requires `base_commit` as above plus report column/table with `CHECK(json_valid(...))` optionally.
- **Pros**: F-02 satisfied by construction (single write); report survives worktree removal; fast reads; audit-friendly; matches spec wording "computed once at top-level".
- **Cons**: More DDL (report column/table) and write path to test; must handle idempotency if `resyncExecution` runs multiple times (completed→completed re-entrance); migration for existing executions (no base → cannot compute retroactively). Slightly more complex.
- **Effort**: Medium-High. Two nullable columns (or one + table) + terminal hook + read path.

### 3) Pure-Go git (go-git / `modernc.org/sqlite` style) without shelling `git`
- **Description**: Use a pure-Go git library to open repo, resolve `base_commit` tree, walk worktree filesystem, compute `changed_files` without spawning `git`. Would add new dependency.
- **Pros**: No external binary, hermetic.
- **Cons**: Violates "pure Go/no cgo without new dependencies" constraint (`openspec/specs/v2-path-claims/spec.md:9` and `openspec/specs/v2-composicion/spec.md:9` both say MUST be pure Go without new deps); reinvents `git diff --find-renames` semantics and untracked/ignore handling; higher risk of F-03 mismatch vs real git. Not viable.
- **Effort**: High, and disallowed by constraints.

## Boundaries / Non-Goals (confirm with sources)

- **No content diffs / line stats** — only paths (`changed_files: string[]`, `tecnica.md:517`).
- **No per-step/per-workflow grouping** — F-02 forbids internal sub-reports (`constitucion.md:IX.5.2`); report is one list per top-level execution regardless of flattened workflow nodes (`tecnica.md:562-563` composition guarantees one execution_id).
- **No commit/push/merge/publish/discard** — `constitucion.md:I.6` Haro never integrates/publishes/discards; report is read-only over worktree state (`IX.1`). `v2-distribucion` owns publishing.
- **No broker/UDS/JSON-RPC in this change** — deferred per `archive-report.md:42-45` and `spec.md:92`; implement CLI-direct (`haro report`) and keep engine method broker-ready (when `v2-broker`/`v2-ipc` land, `execution.report` will thinly wrap `Engine.Report`).
- **No PTY / terminal / distribution** — `AGENTS.md: Out of scope: Embedded terminal/PTY deferred`; `deltas-acceptance` `v2-distribucion` boundary.
- **No `leases`/`interactions` tables or other `v2-store` DDL** — `v2-store` owns remaining DDL; this change solely owns reporting columns/table (mirror `path_claims`/`attempt_transport` sole-owner pattern).
- **No `agents_command`/`agentsFile` artifacts** — excluded per `v2-composicion` spec.

## Risks

- **Worktree lifetime vs report computability** — `engine.go:1019-1023` deletes the worktree immediately when execution becomes `completed|failed`. If report is computed only on `haro report` after that, `workspace_root` no longer exists and `git diff` in that path fails. Mitigation: persist `base_commit` and compute before removal (persisted variant), or make report resilient to missing worktree by diffing from repo root (`git -C <root> diff <base> HEAD -- <execution workspace files>`) and documenting ordering.
- **Starting point ambiguity** — detached worktree (`manager.go:46` `git worktree add --detach HEAD`) has no branch; should report diff against the commit HEAD pointed at creation, not against current `main` tip which may have moved. Must capture SHA at `CreateExecution` (e.g., `git rev-parse HEAD` in `resolvedRoot` before worktree creation) and store it. Risk: capturing SHA after worktree creation reads detached HEAD correctly but if repo was dirty at creation, uncommitted changes would be invisible — spec says "relative to the starting point" (likely committed base, not dirty working tree).
- **Untracked files** — `git diff --name-only HEAD` omits untracked files; `git status --porcelain` includes them (`??`). Execution that `produces` new files (e.g., `internal/execution/engine.go:592-609` artifact snapshots) creates untracked files in worktree — must appear in report. Fix: union `git diff --name-only HEAD` + `git ls-files --others --exclude-standard` (or parse `git status --porcelain=v1 -z`).
- **Renames** — spec says "renamed if applicable" (`deltas-acceptance.md:403`) and "renamed" in U-01 (`:407`). `git diff --name-status` reports renames as `R100 <old>\t<new>` only with `--find-renames`. Must decide: report `changed_files` as new path only (typical) or both old+new. Standard is new path; proposal must lock this and match `git diff --name-status --find-renames` interpretation.
- **Ordering/determinism** — `changed_files` should be sorted (lexicographic) and de-duplicated; unsorted output breaks F-03 comparison and test determinism.
- **Symlinks/canonicalization** — `v2-path-claims` canonicalizes via `claim.Canonicalize` with `EvalSymlinks` anchored to repo root. Report should return repo-relative canonical paths; symlinked files must not produce `../` escapes. Need to filter or canonicalize diff output.
- **`.haro/` internals** — `store.db`, `.haro/worktrees/*`, `.haro/artifacts/*` are inside repo root; naive `git status` would include them if they are tracked/untracked. Report should exclude `.haro/**` (or document inclusion) to avoid noise; verify `.gitignore` contains `.haro/worktrees/` (`tecnica.md:562` says it does).
- **In-progress behavior** — spec says "when execution finishes" (F-01). What should `execution.report` return for `running|pending`? Must fail closed (e.g., `code: not_completed`) or return empty with warning — not silently return partial. Needs explicit error code.
- **CLI-direct shape** — without broker, method exposure is via `internal/cmd`. Prior changes used `run, steps next, step run, status`. Introducing `report` must not collide with future `execution report` vs `status --report`. Must pick one and keep JSON parity (`{changed_files: string[]}` vs `{execution_id, changed_files}`).
- **Constraint leakage** — adding dependencies (e.g., `go-git`) would violate `pure Go/no cgo without new deps`; adding `leases`/`interactions` tables would trespass on `v2-store`. Proposal must scope DDL ownership strictly to reporting columns/table.
- **Test hermeticity** — report tests need real git repos; must be gated (`t.Skip` when `exec.LookPath("git")` fails, `testing.Short()` skip) and use `t.TempDir()` file-backed SQLite, matching existing `worktree/manager_test.go:47` pattern.

## Open Questions for Proposal

1. **What is the canonical "starting point"?** `HEAD` SHA at `CreateExecution` in repo root vs execution row vs captured `git rev-parse HEAD` inside new worktree vs clean snapshot. Does a dirty working tree at creation count (uncommitted changes not in base)?
2. **When is report computed?** At terminal transition (persisted once, satisfies IX.5.2 literally) vs lazily on `execution.report`/`haro report` (logical once, simpler). If eagerly, how to handle idempotency on repeated `resyncExecution` calls?
3. **Persisted or on-demand?** New `executions.base_commit TEXT` (+ optional `changed_files TEXT` / `execution_reports` table) vs stateless recomputation. Migration ownership and nullability for pre-existing executions.
4. **Untracked handling** — must `changed_files` include untracked new files? `git status --porcelain` says yes; `git diff --name-status` alone says no. Which oracle does F-03 use?
5. **Rename semantics** — report single new path vs `old→new` pair? Is `--find-renames` enabled? What similarity threshold?
6. **Ordering/determinism** — sorted output? Case-sensitive? De-duplication rules?
7. **Symlink handling** — should report follow `v2-path-claims` canonicalization (repo-relative, symlink-free)?
8. **CLI surface** — `haro report <execution_id> [--json]` vs `haro execution report <id>` vs `haro status --report`? JSON shape `{changed_files}` vs `{execution_id, changed_files, base_commit}`?
9. **In-progress error code** — `execution.report` on non-terminal execution: `code: not_completed` vs `invalid_state` vs empty list?
10. **Filtering `.haro/**`** — exclude `.haro/` internals from `changed_files`? If yes, how to test F-03 fixture that modifies only `.haro/artifacts`?
11. **Shared vs isolated workspaces** — for `workspace_mode=shared` (`executions.workspace_mode='shared'`, `WorkspaceRoot==root` per `engine.go:111`), report diffs against repo root directly; does it need `--work-tree` handling or just `cwd==root`?
12. **Worktree removal timing** — should `resyncExecution` retain worktree until first successful `execution.report`, or always prune? Who owns cleanup if report is persisted?
13. **Constitution I.6 compliance** — confirm report never auto-commits or resets; purely `git diff/status` read-only.

## Recommendation

**Adopt Approach 1 as baseline, with Approach 2 persistence as additive once terminal-hook tests exist.** Capture `base_commit` at `CreateExecution` (run `git rev-parse HEAD` in `resolvedRoot` before/after worktree creation, persist to new `executions.base_commit` via idempotent `ALTER TABLE` owned by `v2-reporte`), implement pure `ChangedFiles(ctx, executionID) ([]string, error)` in `internal/execution` that shells `git diff --name-only --diff-filter=ADMR` + `git ls-files --others --exclude-standard` (or `git status --porcelain`) with `--find-renames` semantics, sorting and `.haro/**` filtering. Expose via CLI-direct `haro report <execution_id> [--json]` (or `execution report`) delegating to `Engine.Report`; keep JSON-RPC `execution.report` as thin future wrapper when `v2-broker` lands. First deliver on-demand with table tests covering new/modified/deleted/renamed + untracked (file-backed SQLite + temp git repos, gated on `git` presence); add persisted `changed_files` column/table in a follow-up slice if F-02 "computed once" needs literal persistence.
