- **Migration idempotence & transactionality (U-02)**:
  - Idempotence: all `CREATE TABLE/INDEX IF NOT EXISTS` + two `PRAGMA table_info` guarded `ALTER TABLE ADD COLUMN` with duplicate-column swallow (`isDuplicateColumnError`) — proven idempotent over 3 reopens (`migrations_dag_test.go:127-131`, `migrations_report_test.go:126-130`).
  - Transactionality: `migrate` (`:105-118`) executes statements sequentially via `db.ExecContext` **without an enclosing transaction** (`BEGIN`/`COMMIT`). `Open` does not wrap `migrate` in `WithTx`. If `ExecContext` fails mid-loop, earlier tables remain created, later tables not — partial state left, but re-running `Open` will finish remaining statements due to `IF NOT EXISTS`, so final state converges, yet the spec's "mid-way failure leaves no partial state" (atomic) is **not** satisfied. Prior changes accepted this relaxed atomicity (all migrations so far are `IF NOT EXISTS`-only, so partial state is recoverable as "idempotent re-run fixes it", not "no partial state"). For strict U-02 transactional guarantee, `migrate` should wrap the whole statement list in a transaction (or use `BEGIN IMMEDIATE` / `tx.Exec` loop + commit/rollback). `WithTx` helper already exists.

## Approaches

### 1) Complete DDL + repository facade + fake backend in one coherent change (single SDD slice)

- **Description**: In one `v2-store` change, create the 2 missing tables (`leases`, `interactions`) with exact §2 DDL (CHECKs, UNIQUEs, FKs, indexes) via idempotent `CREATE TABLE IF NOT EXISTS`; add `LeaseRepository`/`InteractionRepository` and extend `Store` facade; wrap `migrate` in a transaction for U-02; provide a `FakeStore` (in-memory map-based) implementing the full `Store` interface with constraint enforcement; define a shared domain suite that exercises state machine, lease fencing, claims, events, and interactions against both backends without domain code changes; fix the sole `database/sql` outside-store import; add CI gate script; keep `path_claims`/`attempt_transport`/`dag_hash`/`base_commit` untouched (verify-not-redefine per sole-owner pattern).
- **Pros**: Single source of truth for DDL; F-02 literal ("implements the reference tables") satisfied atomically — no split migration risk; U-01 and U-02/U-03 close together (reviewer sees full contract at once); leverages existing precedent that `v2-adapter` delivered 3283 lines under `size:exception` and current review budget is 200000 lines (size not limiting; task explicitly notes coherence > size); keeps SDD archive history clean (one `v2-store` entry owns the remaining DDL, matching `deltas-acceptance.md` tracking expectation of one SDD change per spec). No circular dependency between DDL and fake.
- **Cons**: Larger diff (~800-1200 lines: 2 DDLs + 2 repos + fake + suite + tests + gate/migration-tx fix); requires careful fake fidelity (CHECK/UNIQUE/FK semantics must match SQLite error shapes or domain suite must be error-shape agnostic). Heavier single review, but within stated budget.
- **Effort**: Medium. Two tables small; fake dominates but is bounded (maps + mutex + cursor counters + `WithTx` copy-on-write). Uses proven `claim.go`/`transport.go` patterns and `claim_test.go` file-backed harness.

### 2) Split DDL-only first, facade/fake second (two-step SDD)

- **Description**: Step A: add `leases`/`interactions` DDL + repo stubs (or repo without fake) and transactional wrap. Step B: add `FakeStore` + interchangeable suite + gate.
- **Pros**: Smaller per-PR diffs; DDL lands early, unblocking `v2-broker` lease runtime sooner; isolates migration risk from fake-fidelity risk.
- **Cons**: Splits the 6-criteria spec across two archive entries — tracking table expects one `v2-store` SDD change with 6 criteria (F-01..U-03) and one `sdd-verify` run covering all; splitting forces either a meta-change or deferred verification for F-02 vs U-01; increases coordination overhead (two proposals/specs/designs for one D07 delta); contradicts the established vertical-slice pattern where `v2-path-claims` and `v2-adapter` each owned their table + behavior together successfully.
- **Effort**: Medium (sum same as #1 but split).

### 3) Interface-only with mocked DB (no real SQLite change)

- **Description**: Declare `LeaseRepository`/`InteractionRepository` interfaces and a `MockStore` (testify/gomock style) that satisfies interfaces via generated mocks; keep DDL deferred to a future migration; verify F-02 by mock expectation rather than real schema inspection.
- **Pros**: No migration risk; interfaces land fast.
- **Cons**: Fails F-02 literally (spec: "inspection of the schema created by the system (without manual migrations) against the reference DDL" — mocks don't create schema, so verification fails); U-02 transactional schema cannot be proven with mocks; U-03 enum CHECKs need real DB constraint enforcement (mocks would simulate via Go checks, not DB); leaves `v2-store` incomplete per tracking table; violates sole-owner pattern where real DDL is the ground truth (all prior changes used real `modernc.org/sqlite` file-backed DBs, never pure mocks).
- **Effort**: Low initial, High debt (requires real DDL later anyway).

### 4) Full 11-table re-migration ownership (takeover)

- **Description**: Re-own all 11 tables in `v2-store` by re-declaring `projects`/`executions`/…/`path_claims`/`attempt_transport` DDL in one canonical migration, treating prior sole-owner tables as re-verified.
- **Pros**: Single canonical DDL file; eliminates cross-change ownership nuance.
- **Cons**: Directly violates established sole-owner contracts (`attempt_transport` sole owner `v2-adapter`, `path_claims` sole owner `v2-path-claims`, `dag_hash`/`base_commit` owners `v2-composicion`/`v2-reporte` — all documented as "verify but MUST NOT redefine" with `CREATE TABLE IF NOT EXISTS` retention). Re-declaration risks divergence (column order, defaults, index names, FK names) and breaks `go test ./...` assumptions built over 4 cycles. Requires re-validating 9 already-correct tables for no benefit.
- **Effort**: High, Negative value.

## Recommendation

**Adopt Approach 1 (complete DDL + facade + fake backend in one coherent change).**

**Justification:**

- **Literal F-02 compliance**: Deltas line 419 says "the schema implements the reference tables: projects, executions, execution_steps, generations, attempts, attempt_transport, leases, step_transition_events, attempt_events, interactions, path_claims — with their constraints and enum CHECKs." The spec's verification is "inspection of the schema created by the system (without manual migrations) against the reference DDL." Deferring `leases`/`interactions` DDL (even if broker runtime is deferred) would make the schema inspection fail — the table is missing, so F-02 is not met. The table is **persistence, not broker runtime**: storing a lease row and enforcing `PRIMARY KEY(execution_id, step_id)` + `CHECK`/`FK` is a store concern; fencing enforcement (VI.1/VI.2) and renewal are broker concerns. Creating the table now as DDL-only (with `IF NOT EXISTS` + repo stubs that satisfy `Store` interface) follows the same precedent that created `path_claims` in `v2-path-claims` even though the broker wait-queue is deferred, and `attempt_transport` in `v2-adapter` even though `v2-store` was pending — both were DDL-pure yet landed eagerly because their specs said "implement the table."
- **Sole-owner coherence**: The "verify but MUST NOT redefine" pattern already solves the apparent tension. `v2-store` must **create only the 2 tables it sole-owns** and add value to `migrations.go` without re-declaring `path_claims`/`attempt_transport`/`dag_hash`/`base_commit`. Those are verified in the final `TestMigrations` 11-table assertion but created elsewhere via `IF NOT EXISTS`. This is documented in `tecnica.md:557-563` and archive reports — no divergence if `v2-store` respects `IF NOT EXISTS` and documents ownership in `design.md`'s migration section.
- **Precedent on size**: `v2-adapter` at 3283 lines already exceeded the historical 400-line budget and was approved via `size:exception` with candidate justification; `v2-composicion` and `v2-reporte` also delivered substantial slices. The task explicitly states the review budget for this session is 200000 lines and "size is NOT limiting, but change coherence is." A complete `v2-store` (~1k lines) is coherent: one spec, one migration, one facade extension, one fake, one interchangeability suite — a single archive entry matches the `deltas-acceptance.md` tracking expectation.
- **U-01 domain suite scoping without broker bleed**: The interchangeable suite does not need the broker daemon. Realistic domain today is: (a) state machine (claim/finalize/reopen/skip) already in `internal/execution/state.go` + `generations` invalidation, (b) lease fencing (acquire/renew/release token semantics) tested against both backends without a daemon loop, (c) path claims behavior matrix already proven, (d) monotonic cursor & `payload_ref` invariant for `attempt_events`/`step_transition_events`, (e) interaction CAS (same `idempotency_key` → same result, different key → rejected, wrong attempt → rejected). All are `Store`-level or `Engine`-level pure operations. Broker's role (holding, expiring, forbidding writes after expiry) can be expressed as repo-level checks (`fencing_token` compare at `UpdateStatus`) without a running daemon — the fake implements the same check as SQLite.
- **U-02 transactional clarity**: Wrapping `migrate` in `BEGIN`/`COMMIT` is a 10-line fix that makes the "mid-way failure leaves no partial state" criterion satisfiable. Without it, the spec's transactional requirement is permanently unmet even though `IF NOT EXISTS` makes re-runs converge. Doing it in the same change that adds the last two tables de-risks future migration evolution.
- **Risk containment**: The residual risk is fake fidelity. Mitigate by having `FakeStore` return `sqlite`-shaped constraint errors (string contains `CHECK constraint failed` / `UNIQUE constraint failed` / `FOREIGN KEY constraint failed`) so domain suite error paths are portable, or make the suite error-shape agnostic (assert `err != nil` + constraint category via typed sentinel from store). Keep the fake in `internal/store` (not `internal/execution`) so it never imports `modernc.org/sqlite`.

## Risks

- **Migration divergence with sole-owned tables (HIGH if ignored, LOW with discipline)** — If `v2-store` re-declares `path_claims`/`attempt_transport` or adds columns to `executions` that `v2-reporte`/`v2-composicion` sole-own, the next `migrate` merge will diverge from archived DDL and break `PRAGMA table_info` guards. Mitigation: `v2-store` DDL block lists only `leases` + `interactions`; existing tables referenced only in verification assertions (`TestMigrations` 11-table check) with comment "verify not redefine — sole owners retained."
- **`leases`/`interactions` runtime vs DDL bleed (MEDIUM)** — Spec expects the tables, but broker runtime (expiry, fencing token increment, `Renew` loop) belongs to `v2-broker`. Building lease expiry timers or interaction queuing now would duplicate broker charter. Mitigation: scope `LeaseRepository` to pure CRUD + fencing-token compare, document `Renew`/expiry as no-op/stub with `TODO(v2-broker)` and tests that only assert token monotonicity, not time-based expiry.
- **Fake fidelity drift (MEDIUM)** — Fake that does not enforce CHECK/UNIQUE/FK or cursor monotonicity will make U-01 pass trivially while SQLite fails. Mitigation: fake's `Create` paths explicitly validate enum domains (same sets as CHECKs), enforce `UNIQUE(attempt_id, idempotency_key)` via map lookup returning constraint error, enforce FK via existence check, enforce `UNIQUE(attempt_id, cursor)` via counter compare; add a `TestFakeParity` that inserts invalid enums into both backends and asserts both reject.
- **`PRAGMA` per-connection for `claim.Acquire` dedicated `Conn` (LOW-MEDIUM)** — `store.Open` sets `foreign_keys=ON` on `db` handle before `migrate`, but `claim.Acquire` opens a dedicated `Conn` via `db.Conn` and runs `BEGIN IMMEDIATE` without re-asserting `PRAGMA foreign_keys=ON` — FK on `path_claims(project_id→projects)` via that Conn may be off, allowing orphan claims. Existing tests pass because FK violation is tested via `s.db.ExecContext` not via `Acquire`. Fix: set pragma on Conn immediately after acquisition or set `PRAGMA foreign_keys=ON` at `Open` via `sql.DB` hook that applies to all pooled connections (modernc supports `pragma=foreign_keys(1)` DSN param — evaluate). Keep fix in `v2-store` as low-risk pragma hygiene.
- **U-02 transactional test determinism (LOW)** — Simulating mid-migration failure portably is fragile (inject bad SQL). Mitigation: test U-02 by opening with an injected failing statement via a test-only `migrateWithStatements` helper that returns error mid-list, asserting prior statements rolled back (0 tables or all-or-nothing), then re-running without injection succeeds. Keep test file-only, not affecting production `Open`.
- **Import gate false positive on `database/sql` (LOW)** — If CI gate checks `database/sql` strictly, `internal/execution/report.go:6` will trip F-01 until fixed. Mitigation: fix import in this change (replace `sql.ErrNoRows` with `strings.Contains(err.Error(), "no rows")` + new store sentinel).
- **Out-of-scope creep** — `base_commit`/`dag_hash` columns belong to `v2-reporte`/`v2-composicion` and must not be altered (task explicitly forbids redefining them). Also `attempt_transport` extension `extra` JSON handling, `path_claims` prefix semantics remain owned elsewhere. Any edit there would violate sole-owner pattern and pollute `go vet` / archive history. Mitigation: `v2-store` proposal/design explicitly enumerates out-of-scope artifacts with `grep` guardrails (no broker/UDS/PTY/reporting/distribution/`base_commit`/`dag_hash` touch).

## Open Questions for Proposal

1. **Lease table FK and CHECK shape** — Spec DDL `:201-209` shows `leases` with `PK(execution_id, step_id)` but no explicit FK to `execution_steps` or `executions`, and no CHECKs. Should `v2-store` add `FOREIGN KEY(execution_id, step_id) REFERENCES execution_steps` + `CHECK(holder<>'')` or keep spec verbatim (no FK) to match reference exactly?
2. **Lease repository naming** — Spec §5 shows `LeaseRepository` (singular) vs `Leases()` on `Store`; existing code uses `PathClaims()` plural. Which canonical name does the proposal lock — `Leases() LeaseRepository` vs `Leases() LeasesRepository`?
3. **Interaction repository surface** — F-02 lists `interactions` table but spec §5 does not define `InteractionRepository` interface. Does `v2-store` define `Interactions() InteractionRepository` with `{Create, Get, Resolve(idempotency_key), List}` or defer method surface to `v2-broker`/`v2-ipc` specs?
4. **Fake error shape** — Should `FakeStore` return `sqlite`-verbatim errors (`CHECK constraint failed: ...`) or typed sentinels (`ErrCheckFailed`, `ErrUniqueViolation`, `ErrForeignKey`) that both backends map to? Domain suite must be error-shape agnostic — which shape does the spec's U-03 "constraint error" verification expect?
5. **Transactional test injection** — Does U-02's "simulate mid-migration failure → consistent state" require a test-only injection hook in `migrate` (test helper) or can it be proven via external kill of the `Open` process mid-DDL?
6. **Per-Conn pragma handling** — Should `claim.Acquire`'s dedicated `Conn` path re-execute `PRAGMA foreign_keys=ON` + `journal_mode=WAL` or rely on DB-level pragmas propagating to pooled connections via DSN `?_pragma=foreign_keys(1)`?
7. **`database/sql` import gate scope** — Does F-01's verification gate check `database/sql` or only `modernc.org/sqlite`? If both, `internal/execution/report.go:6` must drop the import in this change; if only driver, the import remains permissible as a sentinel carrier.
8. **Domain suite location** — Should the interchangeable suite live as `internal/store/interchangeable_test.go` (store-level only) or `internal/execution/domainsuite` (engine-level state machine + leases + claims + events + interactions together)?
9. **Broker lease expiry semantics deferral** — Lease `expires_at` and fencing increments are DDL-only in `v2-store`; does the repo's `Acquire` generate `fencing_token` as `max+1` or `rand` or `time`-derived? Spec only says `INTEGER NOT NULL` — proposal must pick.
