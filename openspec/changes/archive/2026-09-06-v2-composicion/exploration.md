## Current State

### How composition is treated today (read-only mapping)

* **Workflow YAML parsing — minimal subset only.** `internal/workflow/parse.go:10-38` defines `Workflow{Version,Name,Workspace,Steps}` and `Step{ID,Type,Run,Env,TimeoutSeconds,DependsOn,Requires,Produces,Harness,Instructions,Mode,Workspace}`. There are **no** fields for `Source`, `Bindings`, `Inputs`, `Outputs` (`docs/v2/haro-especificacion-tecnica.md:23-47`, `102-114`). `Parse()` (`parse.go:69-85`) validates only `version==2` and `len(steps)>=1`; YAML unknown fields are silently ignored by `gopkg.in/yaml.v3` (no strict decoding, no `inputs/outputs/workspace` contract validation). This diverges from the normative JSON Schema (§1) and from U-04's `zod` mandate — Go side must emulate its strictness with manual validation (`deltas-acceptance.md:387` note: "zod is current repo practice").

* **Validation — `type: workflow` is accepted but inert.** `internal/workflow/validate.go:28` lists `command|agent|workflow` as allowed, but only `command`/`agent` have per-type requirements (`validate.go:31-49`). A `workflow` step passes with just `id`+`type`; missing `source`, illegal `run`, or stray `inputs/outputs` are not checked. No file-graph cycle check (F-05/U-02), no parent-against-contract check (F-03/U-03), no root-file `inputs/outputs` prohibition. DAG validation (`validate.go:69-144`) checks duplicate IDs, missing `depends_on`, cycle via DFS on `depends_on` edges only, and "no entry point" — all **post-flattening** single-file checks, not pre-flattening file-reference cycles. `depends_on` graph is the only edge; `requires/produces` are not DAG edges (correct per Spec 5), but composition adds the binding-wired DAG edges that are currently absent.

* **Planning / Engine — no flattening.** `internal/execution/engine.go:59-164` (`CreateExecution`) discovers `root/.haro/workflows/*/workflow.yaml` via `workflow.Discover` (`internal/workflow/discover.go:21-64`), calls `workflow.Validate`, resolves workflow-level `Workspace` (`engine.go:91-94`), creates `execID = uuid.NewString()` and a worktree at `.haro/worktrees/<execID>` when `isolated` (`engine.go:95-110`), and persists exactly `wf.Steps` unchanged into `execution_steps` (`engine.go:121-155`). No recursive file loading, no namespacing, no bindings. `execution_steps` DDL already supports namespaced IDs (`haro-especificacion-tecnica.md:154`, `migrations.go:28-39` `step_id TEXT` with `type CHECK … workflow`), so schema is ready but population is not.

* **Execution of a `workflow` step — fails closed today.** `internal/execution/engine.go:274-286` `RunStep` dispatches on `step.Type`: `agent→runAgentStep`, `command→` onward, else `unsupported_step_type`. Since `type: workflow` falls into the else, `steps next` would surface it as pending but `step run` would error `unsupported_step_type: workflow` — fail-closed, but not the normative planning-time flattening (should never be runnable; should be expanded before `execution_steps` is created). The correct model per `haro-constitucion.md:X.1.2` and `deltas F-01` is that composition resolves **before any execution exists**, at planning/compilation time; today there is no planning phase distinct from `CreateExecution`.

* **Dependencies / file resolution semantics — undefined.** Spec `tecnica.md §1 props: source` is described as "path relative to another workflow file" (`tecnica.md:105`). The only file-resolution precedent in the codebase is `internal/workflow/discover.go:36` (`(filepath.Join(base,name,"workflow.yaml")`) and engine's `Discover`-then-lookup pattern plus the fallback `os.Open(exec.WorkflowSource)` in `RunStep` (`engine.go:430-445`). No relative-to-parent-file resolution, no `EvalSymlinks`/`ValidateContainedPath` gating for `source`, no depth limit. v2-path-claims added `project.LoadConfig` + `claim.Canonicalize` with root-anchored `EvalSymlinks` (`engine.go:197-214`, `claim/canonical.go`), and `workflow.ValidateContainedPath` (`workflow/path.go:14`) — those patterns will be reused for `source` containment.

* **Workspace isolation & claims — must compose.** `v2-path-claims` introduced: `WorkspaceConfig{Mode,OnLogicalConflict}` parsing + `ResolveWorkspace` (`parse.go:40-65`), inheritance `system→workflow→step` (`engine.go:139`), `worktree.Manager` (`internal/worktree/manager.go`) with `Create/Remove/Prune` via `exec.CommandContext git worktree add --detach` at `engine.go:97,159,175`, atomic `PathClaims.Acquire` with `BEGIN IMMEDIATE` prefix scan (`store/claim.go`), canonicalization of `requires ∪ produces` (`engine.go:191-215`), and `releaseClaims` deferred on every return (`engine.go:369,260-272`). Any composition design must: (a) resolve effective `Workspace` per flattened step inheriting from its root workflow and its own override (not from the included file's workflow-level default unless explicitly propagated), (b) create exactly one worktree per top-level execution (`engine.go:91-110`), (c) acquire claims for flattened `requires ∪ produces` at `RunStep`, and (d) not break `steps next` filtering of `logical_conflict` (`cmd/execute.go`).

* **Invalidation cascade — X.4 not implemented.** `internal/execution/state.go:22-71` `ReopenStep` builds descendant set by walking `depends_on` edges transitively from `stepID` (`state.go:33-50`), invalidates generations via `Generations().InvalidateByStep` (`store/repositories.go:219`), and force-transitions to `pending`. Generation handling in `RunStep` (`engine.go:355-401`) creates a new generation per run and `state.go:21` tracks `invalidated_at`. Current `requires` staleness check (`engine.go:321-354`) iterates all steps that `produce` the required name and rejects if any associated generation has `invalidated_at != nil` — coarse, not per-binding fine granularity. X.4 (`constitucion.md:178-183`, `deltas F-06`) requires cascade on the **flattened real artifact graph** (`produces` feeds `requires`), independent of declared `inputs/outputs` — today bindings don't exist so this behavior cannot be validated.

* **Storage interfaces — ready for extension.** `internal/store/store.go:152-231` facade exposes `Store{Projects,Executions,Steps,Attempts,Generations,Events,Transport,PathClaims,WithTx,Close}`. `Executions` holds `WorkflowSource` (root YAML path), `ExecutionStep` holds `DependsOn/Requires/Produces` as JSON strings, `type` CHECK includes `workflow` (`migrations.go:32`). `WithTx` (`store.go:231-250`) is used by `CreateExecution` to insert execution+steps atomically — composition must expand inside that txn. No `DAG hash` column or flattened-DAG persistence beyond steps; structural equality (U-01) will need a deterministic serialization/hash.

* **Fixtures & test patterns.** Only `testdata/sample-workflow.yaml` (`version:2, name:sample, steps:[build command]`) exists. Test conventions: `internal/workflow/*_test.go` — `Parse` with `strings.NewReader`, `t.TempDir`, table-driven (`validate_test.go:49-94` cycle/duplicate/missing tables), `workspace_test.go:8-84` `ResolveWorkspace` tables. Engine tests use `store.Open(t.TempDir()+"/db")` file-backed (never `:memory:`) and `FakeWorktree`/`FakeRunner` injection via `SetWorktreeManager` (`engine.go:54-57`) and seeded `CommandRunner`. DAG cycle tests in `validate_test.go` use DFS detection; no file-graph tests exist. DAG hash / structural equality pattern does not exist — to be invented for U-01 (`tecnica.md:121` stable topological order is the spec hint).

* **`.haro/config.yaml` interaction.** `internal/project/config.go` handles `external_paths` minimal list (empty default), preserved through v2-path-claims. No composition-specific config is specified; `source` resolution ignores config. `system` workspace default (`isolated`) is hardcoded (`parse.go:42-44`, `engine.go:91`) rather than read from `config.yaml` `defaults.workspace` — consistent with spike.

## Approaches

### Approach 1 — Recursive planning-time flattening inside `CreateExecution` (recommended baseline)

Expand `workflow` steps depth-first at planning time, before the `WithTx` insert. Pseudo:
```
flat, err := compose.Flatten(rootAbsPath, os.ReadFile) // pure, returns FlatSteps+hash
if err != nil { return "", typedValidationError } // fail before execution row
write flat.Steps to execution_steps
```
`Flatten` is pure: takes `ReadFile func(string)([]byte,error)` and the root bytes, returns `FlatDAG`. Static cycle detection runs on the file-reference graph (canonicalized absolute paths, `EvalSymlinks` for identity, covers direct/self/transitive even when node names differ) **before** DFS into contents — satisfies F-05/U-02. Namespacing is string prefix `node + "." + internal` recursively (handles nested composition: `a.b.c`). Bindings rewiring: for each `workflow` node, look up its included file's `Inputs/Outputs`, validate `bindings` keys ⊆ declared set, then rewrite each flattened internal step's `Requires/Produces` through the bindings map and rewrite inter-step `depends_on` to namespaced IDs. Parent `depends_on` that targets a `workflow` node stays as-is but its internal steps' `depends_on` that edge into parent-external steps are expanded via declared `inputs` (i.e., internal consumer `satisfied_by=input` inherits parent's `depends_on`). Topological stability comes from sorting internal steps by original file order then namespaced ID.

- Pros: Single owner (`workflow` + `execution`), minimal engine churn, purely additive `internal/workflow/compose.go` + validator splits; transactional — if flatten fails, no `execution_id` or worktree is created (fail-closed `I.3`); U-01 purity is trivial to test (`Flatten` twice same hash, no DB); composable with v2-path-claims claims/worktree because flattened `requires/produces` are just more steps.
- Cons: `CreateExecution` must read multiple files — I/O inside validation path; deep nesting risks stack overflow without guard (depth limit e.g. 16 requested); `source` resolution relative to parent file is subtle vs `Discover`-based canonical workflow names.
- Effort: Medium (≈3-4 focused PR slices). File count fits the 400-line guard with chaining.

### Approach 2 — Separate `planner` service / package that engine calls

Extract a new `internal/planner/` package exposing `Plan(rootPath, workflowName) (*Plan, error)` that encapsulates `Discover + Flatten + ValidateFlat`. Engine becomes `store + planner + runner + worktree`.

- Pros: Clean separation, planner independently testable, isolates file I/O/composition concerns from execution lifecycle; mirrors `internal/claim` split in v2-path-claims which reviewers liked (`archive-report.md:41` file-changes table).
- Cons: Extra package/indirection for a single-call-site feature; introduces a new facade over `workflow` that risks duplicating `Discover` semantics (`discover.go:21-64`) and `Validate` split; slightly higher review cost (more files). Doesn't change core risks of cycle/namespacing.
- Effort: Medium-High (one extra package, same flatten logic plus wiring).

### Approach 3 — Lazy runtime expansion (expand `workflow` steps on first `steps next`/`step run`)

Keep `CreateExecution` storing the raw tree (`workflow` nodes as persisted steps), expand workflow nodes only when requested. Child steps materialize lazily with the same namespacing but execution row already exists.

- Pros: Planning is cheap; allows inspecting the workflow tree before expansion; incremental migration (no change to creation path).
- Cons: Violates constitution X.1.2 ("There are no 'child' executions: the result is a single flat DAG under a single `execution_id`" at *planning* time) and `deltas F-01` verification ("composition happens at planning time", `run` fails with cycle *without a created execution*). Lazy expansion would create an execution before knowing cycle errors, and would need a second transaction to replace `workflow` nodes — complex, non-pure, and breaks U-01 reproducibility (hash would mutate over time). Grossly incompatible with `WithTx` atomicity and lease/idempotency assumptions.
- Effort: High and normatively invalid — rejected.

## Recommendation

**Approach 1** — recursive planning-time flattening inside `CreateExecution` backed by a pure `internal/workflow/compose.Flatten` function.

- Matches every normative hint ("composition happens at planning time; result is ONE flat DAG under ONE execution_id with NO child executions; namespacing; inputs/outputs/bindings; static cycle detection before flattening; §X.4 invalidation ignores boundary" per `constitucion.md:160-188` and `deltas-acceptance.md:344-390`). Approach 3 violates that directly.
- Keeps blast radius small: two new small files (`compose.go`, `hash.go`) + edits to `parse.go`, `validate.go`, `engine.go`, `state.go` — aligned with prior v2-path-claims delivery slices (`archive-report.md:15` work units) and the 400-line guard.
- Pure `Flatten` satisfies U-01's "same YAML → same flat DAG" and enables Go's standard race-safe table tests (`go test ./... -race`) without DB. The only I/O is injected `ReadFile`, so unit tests use in-memory fixtures while integration tests use `t.TempDir` files (pattern from `workflow/parse_test.go:52-118` and `store/migrations` file-backed DB rule from `archive-report.md:13`).
- Preserves `v2-path-claims` invariants: one worktree per execution, atomic `path_claims` with prefix scan, owner-checked `Release`, and `steps next` blocking — none are touched.
- Error handling maps directly to the tracking criteria: structured `{code, field, message}` errors with field paths (`bindings.foo`, `inputs[0].satisfied_by`, `source`) are returned before any `execution_id` is minted, satisfying F-05's "without a created execution" and U-03/U-04's "specific validation errors" and `haro-constitucion.md I.3` fail-closed.

If the proposal wants maximal testability isolation, graft Approach 2's package shell (`internal/planner`) onto Approach 1's core algorithm — no behavioral difference. Prefer starting as Approach 1 and extracting `planner` only if `engine.go` churn exceeds the 400-line budget.

## Risks

- **CRITICAL — Double-write of file identity / symlink escape in `source`:** `source: ../other.yaml` could escape `root/.haro/workflows` into arbitrary FS if resolved naïvely (mirrors the `CRITICAL symlink escape` risk mitigated in `claim/canonical.go` and `workflow/path.go:14`). Mitigation: resolve `source` relative to including file's directory, then `filepath.Clean`, `EvalSymlinks` on the resolved absolute, then enforce containment within `root` (or allow sibling workflows outside `.haro/workflows` explicitly via spec decision). Reject absolute, `..` that escapes `root`, and symlink that re-enters via outside path with a `field:"steps[i].source"` error.
- **Cycle identity confusion:** Two nodes `a` and `b` both `source: same.yaml` is NOT a cycle; `a.yaml → b.yaml → a.yaml` with different node names IS a cycle. Mitigation: canonicalize files by realpath (`EvalSymlinks`), not by node name. Include direct, transitive, self (`a → a`) in `U-02` table.
- **Namespace collision / length:** Recursive prefix `a.b.c.d.step` can exceed filesystem/DB length constraints or shadow a real step ID in parent. Mitigation: `Step.ID` pattern `^[a-z][a-z0-9_]*$` (`tecnica.md:72-73`) applies per segment; validate post-namespacing uniqueness; document max depth (16) and total namespaced length limit.
- **Bindings silent mis-wiring:** If `bindings` maps `my_input → parent_requires_value` but parent's `requires` doesn't contain that value, artifact identity silently diverges (parent never acquires the claim for the internal requirement). Mitigation: `ValidateFlat` cross-checks that every `bindings` key is a declared `input/output` and every declared `input`'s `satisfied_by` internal step actually `requires` that input name; similarly `outputs` mapping requires internal step `produces` that name.
- **Inheritance ambiguity for nested workflow's internal steps:** `system→workflow→step` inheritance currently resolves (`ResolveWorkspace(wf, stepID)` at `engine.go:139`) using the root workflow's `Workspace`. Nested files also have a `workspace` block — should it be ignored, inherited, or overridden? Per `tecnica.md:121` namespacing note and the v2-path-claims "inheritance" narrowly defined (`archive-report.md:16`), the safe default is: root workflow's `Workspace` governs execution-level `execMode`/`workspaceRoot`; each flattened step's effective `Workspace` is resolved from the **root** workflow+step override, not from included file's workflow-level block. Included file's workflow-level block should be validated for shape but not auto-propagated (proposal must decide; either choice needs an explicit U-03 error if conflicting).
- **Deviation from zod-faithful validation (U-04 audit risk):** Go's `yaml.v3` + manual checks cannot literally call `zod`; reviewers will probe for "exact field" messages. Mitigation: new `ValidationError{Code, Field, Details}` type with table tests asserting `Field` values exactly (e.g. `steps[2].bindings.foo`), feature-parity with `openspec/specs/v2-path-claims` validation tables.
- **File I/O inside `CreateExecution` breaks current `Discover`-only tests:** `engine_claim_test.go` and integration tests use `t.TempDir` + `FakeWorktree`; composition adds N file reads per execution start. Mitigation: inject `ReadFile`/`FS` abstraction for U-01 purity; gate E2E fixture reads with `testing.Short` like `worktree` E2E (`archive-report.md:21` gating).
- **Rollback idempotence:** New files are additive; if reverted, old executions that were created with flattened steps might have persisted namespaced IDs that the reverted code no longer understands. ## Open Questions for sdd-propose

1. **`source` resolution base and containment:** Confirm normative base is **parent file's directory** (so `source: ./sub/workflow.yaml` relative to including YAML). Should containment be enforced to `root` (repo root) or to `root/.haro/workflows`? v1 discards via `Discover` constrain to workflows dir, but nested composition may want sibling directories (e.g., `.haro/workflows/lib/reusable.yaml`). Proposal must pick and encode in validation + tests.
2. **`inputs/outputs` on root file:** Must a root file omit them entirely (fail if present) per `tecnica §1.1` "only valid in the file that is going to be included; a root file may omit them" — tighten to MUST NOT declare on root, or treat as allowed-but-ignored? U-03 requires "declaring `inputs`/`outputs` in a root file → specific validation errors" (`deltas:397`) — implies prohibition. Resolve.
3. **`bindings` completeness:** Must parent's `bindings` cover *all* declared `inputs`/`outputs` of the included file, or may it omit unused ones (and those internals go unwired)? Fail-closed stance suggests missing required binding is an error if the internal step's `requires/produces` is non-empty.
4. **Workspace inheritance for nested internals:** Should an included file's workflow-level `workspace: {mode, on_logical_conflict}` apply to its own internal steps after namespacing, or is it ignored in favor of root+step override? Both are consistent with `ResolveWorkspace` (`parse.go:40-65`) only looking at root workflow's block. Proposal should choose and add a `MODIFIED` requirement that clarifies it, to pin `v2-path-claims` invariants.
5. **Max composition depth / file count:** Propose a guard (e.g., depth 16, total expanded steps 256) to avoid pathological recursion and DB blow-up. This is not in D05 but is expected fail-closed hardening like the 16 KiB / 2 MiB budgets (`deltas F-12`).
6. **DAG hash persistence vs on-read:** Persist `dag_hash` on `executions` for U-01 audit (needs idempotent `ALTER TABLE` migration) or compute deterministically on read? Persisting simplifies verify-report evidence (store `dag_hash` and compare two runs); computing avoids schema change but risks drift.
7. **`zod` fidelity scope:** Since Go cannot depend on `zod`, define the equivalence criterion for U-04: manual validator must reject the same table of invalid YAMLs as a reference zod schema would (include `additionalProperties:false`, `pattern`, `minItems:1`, conditional `required: ["source"]` when `type:workflow`, etc.). Proposal should list that table explicitly so spec reviewers can audit.
